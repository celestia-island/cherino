# Бэкенды

Cherino рассматривает изоляцию контейнеров как задачу «политика поверх
механизма»: платформа предписывает, *что* разрешено (через профили
безопасности), а каждый бэкенд переводит это в свой нативный механизм
(host-конфиги Docker или хуки OCI-спецификации). Все бэкенды реализуют один и
тот же трейт `ContainerOps`.

| Бэкенд | Тип | Платформа | Механизм | Уровень |
|---------|------|----------|-----------|------|
| **Docker** | API | Все | Bollard → Docker Engine HTTP API | основной |
| **Youki** | Native | Linux | libcontainer → rootless-контейнеры OCI | резервный |
| **WSLc** | CLI | Windows | вызовы `wslc.exe` / `container.exe` | резервный |
| **Apple Container** | CLI | macOS 26+ | CLI `container` (по VM на контейнер) | резервный |

## Docker (основной)

Бэкенд Docker используется по умолчанию и является наиболее проверенным в бою
путём. `ContainerManager` подключается к локальному Docker-демону через
Bollard и реализует всю поверхность `ContainerOps`, включая exec, копирование
файлов, снимки, тома и управление образами. Он доступен на каждой платформе за
feature `docker`, включённым по умолчанию.

```rust
use cherino::ContainerManager;

let mgr = ContainerManager::new()?; // local daemon
// or, against a specific socket:
let mgr = ContainerManager::new_with_socket("/var/run/docker.sock")?;
```

## Youki / libcontainer (резервный, Linux)

Crate `cherino-runtime` предоставляет `YoukiManager` — OCI-нативный бэкенд,
построенный на libcontainer. Он **rootless и без демона**: контейнеры
выполняются от имени вызывающего пользователя, без фонового сервиса, что делает
его резервным вариантом для хостов, где Docker-демон недоступен или не
разрешён.

`cherino-runtime` автоматически собирает свой настоящий бэкенд на
`cfg(target_os = "linux")`. На любой другой платформе компилируется заглушка,
чьи вызовы возвращают ошибки «доступно только на Linux», так что
кроссплатформенный код может зависеть от него безусловно.

**Youki — резервный уровень**: он поддерживается как rootless-альтернатива, а
не как основной драйвер оркестрации. Предпочитайте бэкенд Docker всякий раз,
когда демон доступен.

## CLI-бэкенды (резервные, Windows / macOS)

За опциональным feature `cli-backend` cherino поставляет CLI-адаптеры для
контейнерных рантаймов, не предоставляющих стабильного локального API:

- **WSLc** на Windows — вызовы `wslc.exe` / `container.exe`.
- **Apple Container** на macOS 26+ — управление через CLI `container`, который
  запускает лёгкую VM на каждый контейнер.

`cli-backend` по умолчанию выключен; включайте его явно на хостах
Windows/macOS:

```toml
[dependencies]
cherino = { version = "0.1", features = ["cli-backend"] }
```

## Двухуровневая архитектура рантаймов

Платформа celestia использует два различных контейнерных рантайма на разных
уровнях:

| Уровень | Рантайм | Кем используется |
|-------|---------|---------|
| **Внешний** (оркестрация) | Docker/Podman | проверка здоровья TUI, демон scepter, server manager |
| **Внутренний** (песочница cosmos) | Youki/libcontainer | Snowflake manager, состояние агента Neikos |

Внешний уровень управляет инфраструктурными контейнерами (scepter, postgres)
через API Docker/Podman; им нужны полные возможности оркестрации — сеть,
постоянные тома, проверки здоровья, композиция из нескольких контейнеров.
Внутренний уровень (Cosmos) работает *внутри* контейнера scepter и использует
Youki для создания лёгких, быстро запускающихся изолированных контейнеров для
выполнения агентов, каждый со своим профилем seccomp и лимитами ресурсов.

## Флаги features

`cherino`:

- `docker` *(по умолчанию)* — бэкенд `ContainerManager` на базе Bollard.
- `cli-backend` — CLI-адаптеры WSLc / Apple Container. По умолчанию выключен.
- `docker-tests` — интеграционные тесты, требующие работающий Docker-демон
  (по умолчанию выключены; подразумевают `docker`).
